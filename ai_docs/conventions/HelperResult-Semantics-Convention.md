# Helper Result Semantics Convention

本文件用于沉淀 `Lanymy.NET` 在 `Helpers` / `Instruments` 这类通用工具模块中，关于“返回 `false`、结果模型、直接抛异常”三类语义的长期约定。

## 1. 适用范围

- 适用于 `src/Commons/` 下所有对外暴露的通用 Helper / Instrument 入口。
- 适用于文件、网络、进程、邮件、快捷方式、命令执行等“会触发外部操作或环境依赖”的通用能力。
- 不要求对纯内部私有辅助函数强制引入结果模型，但若该函数已经承担对外契约边界，应按本约定收敛语义。

## 2. 总原则

- 默认不要在“错误码”与“直接抛异常”之间做单选题。
- 推荐优先采用“三层语义”：
  - `兼容层`：保留历史 `bool` / `false` / no-op 语义
  - `严格层`：返回 `ResultModel + Exception`
  - `参数错误 / 调用方式错误`：直接抛明确异常，或在严格层中以 `Exception` 显式表达
- 新增能力或现代化改造时，优先补严格层，不要直接破坏历史兼容入口。

## 3. 兼容层约定

- 兼容层用于承接历史调用点，目标是“尽量不破坏旧行为”。
- 兼容层可以继续保留：
  - `bool` 成功/失败
  - 历史 `false` 语义
  - 历史 no-op 语义
  - 少量历史吞异常行为
- 但兼容层若继续保留弱语义，必须满足两个条件：
  - 严格层已存在，可提供完整诊断信息
  - 测试中已明确锁定兼容层的历史行为边界

## 4. 严格层约定

- 严格层是默认推荐给新调用方使用的入口。
- 严格层优先返回结果模型，而不是只返回错误码。
- 结果模型至少应包含：
  - `IsSuccess`
  - `Exception`
- 若场景允许，应进一步补充关键诊断字段，例如：
  - 源路径 / 目标路径
  - 输入地址 / 输出地址
  - `ExitCode`
  - `Status`
  - 批量子项结果集合
- 若一次操作天然存在“部分成功、部分失败”，必须优先考虑聚合结果模型，而不是只返回单一布尔值。
- 若模块原本就已经返回稳定、可诊断的结果型对象（例如 `EncryptDigestInfoModel` 这一类 digest model），则不必为了形式统一再额外套一层 `WithResult(...)`；优先补齐字段、修正成功判定和测试覆盖。
- 对于多层组合入口（例如 `bytes -> file`、`string -> bitmap`、`bitmap -> string`），若返回的是更具体的 digest model，则成功后需要把该层新增语义对应的字段回填完整，不能只依赖下层结果对象。
- 对于“解密后重新组装结果模型”的入口，除了 `Source*` 字段，还要回填类型元数据和原始输入载体字段，避免结果模型在加密侧和解密侧语义不对称。
- 若某类 API 本身已经以 digest model 作为返回值，则内容级失败（例如密钥错误、密文损坏、结构截断）优先回到 `IsSuccess == false` 与明确 `ErrorMessage`，只把参数错误、文件缺失这类调用边界问题继续作为异常抛出。
- 对 `Base64 / Bitmap / ImageFile / JSON` 这类内容载体，若输入格式无效或反序列化失败，也应优先返回失败 digest，并尽量保留原始输入字段，便于调用侧诊断。
- 对 `Stream -> Stream` 这类底层组合入口，若目标流可寻址，失败后应尽量回收已写入的半成品内容，避免把不完整结果留给上层继续消费。
- 结果模型分层要保持克制：通用摘要模型只承载通用字段，文件、图片、模型等载体特有上下文放在对应派生 digest model 中。
- 对“聚合型一次操作”结果，除了子项成败本身，还应保留本次请求的关键上下文（例如目标列表、发送模式、编码），避免失败后只能看到子项错误却无法还原原始调用形态。
- 对集合级参数错误，不要通过伪造一条失败子项来承载异常；优先放在聚合结果自己的批次级字段上，再让子项明细只表达真实执行过的项。
- 对同时保留兼容层和严格层的集合 API，兼容层可以继续沿用“首项失败立即抛异常并中断”的历史行为，但严格层应把已处理项和未处理项的边界表达清楚。

## 5. 何时直接抛异常

- 以下情况默认应直接抛异常，或在严格层中明确产出对应异常对象：
  - 参数为 `null`
  - 参数格式非法
  - 调用顺序明显错误
  - 越界、非法状态、前置条件不满足
- 这些问题本质上更接近“调用方使用错误”或“契约违反”，不应被压缩成模糊的 `false`。

## 6. 何时不要只用错误码

- 对于文件系统、网络、SMTP、COM、进程、反射等底层能力，不建议只返回裸错误码。
- 原因包括：
  - 错误码很难完整承载底层上下文
  - 原始异常类型通常更有诊断价值
  - 后续排查往往需要堆栈、消息和具体异常类型
- 若场景中确实存在稳定、有限、可枚举的失败分类，可在结果模型中补充：
  - `ReasonCode` / `StatusCode` 枚举
- 但该枚举用于“补充分类”，不用于替代异常本身。

## 7. 推荐的判断顺序

面对一个现有弱语义入口，改造时按以下顺序判断：

1. 先判断该失败是否属于“参数错误 / 调用错误”
2. 若不是，再判断它是否属于“外部系统操作失败”
3. 若是外部操作失败，优先落到 `ResultModel.Exception`
4. 若该失败还存在明确稳定的业务分类，再补 `enum` 型失败类别
5. 最后才考虑是否有必要引入单独错误码

## 8. 测试与文档要求

- 只要对入口语义做了兼容层 / 严格层改造，默认都需要：
  - 在 `src/UnitTests/Lanymy.Common.AllTests` 补齐对应回归测试
  - 同步更新对应模块的 `ai_docs/architecture/...` 专题文档
- 测试至少要覆盖：
  - 兼容层历史语义
  - 严格层成功路径
  - 严格层失败路径
  - 参数非法场景

## 9. 当前仓库中的推荐模式

- 当前仓库已经在以下模块采用或正在采用该模式：
  - `CompressionHelper`
  - `FileHelper`
  - `FileSerializeHelper`
  - `JsonSerializeHelper`
  - `ProcessHelper`
  - `EmailHelper`
  - `PcInfoHelper`
  - `NetworkHelper`
  - `SecurityAesHelper`
  - `SecurityHelper`（RSA 密钥 / RSA 加解密 / 证书入口）
- 后续类似入口默认沿同一模式演进，避免：
  - 有的模块返回 `bool`
  - 有的模块抛异常
  - 有的模块塞错误码
  - 最终形成不可预测的 API 语义碎片
