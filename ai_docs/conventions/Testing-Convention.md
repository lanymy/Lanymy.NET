# Testing Convention

本文件用于沉淀 `Lanymy.NET` 在“功能修改 -> 测试补齐 -> 用户回归”这一链路上的长期协作约定。

在本仓库中，“功能回归”不只表示功能正确性验证，还默认包含：

- 性能验证
- 稳定性验证

## 1. 适用范围

- 适用于后续所有会修改功能行为、异常语义、生命周期、状态流转或公共 API 表现的代码变更。
- 适用于 `Helpers`、`Instruments`、`ExtensionFunctions` 及其相关抽象层、聚合层的功能修改。
- 不要求对纯文档修改、纯注释修正、无行为变化的机械重命名强制补新测试，但若改动影响理解或边界判断，仍应评估是否需要补断言。

## 2. 默认规则

- 后续 AI 或协作开发者只要修改了功能代码，默认都需要在 `src/UnitTests/Lanymy.Common.AllTests` 中完善对应的单元测试用例。
- 测试目标不是“为了有测试而有测试”，而是要覆盖本次修改引入或修正的行为契约，并服务于功能正确性、性能表现和稳定性边界的回归验证。
- 若现有测试文件已能自然承接，应优先在原测试文件中补齐用例，而不是重复创建新的测试类。
- 若现有测试结构无法清晰表达本次契约，再新增测试类或测试辅助类型。

## 3. 测试落点原则

- 主测试项目默认落点：`src/UnitTests/Lanymy.Common.AllTests`
- 对 `Lanymy.Common.AppTests` 不追加新的主回归职责；该项目视为历史演示或辅助验证项目。
- 新测试应尽量贴近被修改模块的现有测试组织方式，例如：
  - `Socket` 相关修改优先补到已有 `Socket*Tests.cs`
  - `WorkTask` 相关修改优先补到已有 `WorkTaskTests.cs`

## 4. 回归维度与覆盖要求

- 功能正确性：新增功能至少覆盖主成功路径与关键失败路径；修复缺陷至少覆盖复现场景与修复后的正确行为。
- 性能验证：功能回归用例需要体现关键性能契约，至少覆盖“不会因本次修改明显退化”的核心路径；对高频调用、循环处理、队列/收发链路类改动，应优先补充可重复执行、可比较趋势的轻量性能验证。
- 稳定性验证：功能回归用例需要体现边界稳定性，至少覆盖重入、重复启动关闭、异常上报、资源释放、长时间或多轮调用后状态不失真的场景。
- 生命周期类修改：优先覆盖启动、停止、关闭、释放、重入、异常上报等边界行为。
- 公共发送、接收、队列、过滤器、回调类修改：优先覆盖异常不丢失、状态不乱跳、旧对象不误用，以及在重复调用或批量处理下不出现明显退化的契约。

## 5. 协作分工

- AI / 协作开发者负责：
  - 在 `Lanymy.Common.AllTests` 补齐与本次修改直接对应的测试用例
  - 在测试设计上同时考虑功能正确性、性能验证和稳定性验证三个维度
  - 至少完成受影响文件的诊断检查
  - 在条件允许时完成定向构建或定向测试验证
- 用户负责：
  - 手动运行完整单元测试回归
  - 以完整回归结果确认仓库级稳定性、性能与兼容性是否满足预期

## 6. 例外处理

- 若某次修改确实无法在当前测试基础设施下稳定表达，需要在交付说明中明确写出：
  - 为什么暂时无法补测试
  - 缺失的验证点是什么
  - 缺失项属于功能正确性、性能验证还是稳定性验证
  - 后续应补在哪个测试文件或测试基础设施中
- 若只是“实现很小”或“修改看起来简单”，不能作为不补测试的理由。

## 7. 执行顺序建议

- 先定位功能改动对应的现有测试文件。
- 再补最小但有效的回归型测试用例，并明确覆盖功能正确性、性能验证和稳定性验证中的哪些维度。
- 然后检查相关文件诊断。
- 最后由用户手动执行完整单元测试回归，确认仓库级功能、性能与稳定性。

## 8. 目标

- 让后续功能修改都能在提交阶段留下可复验的功能、性能与稳定性契约。
- 将“功能实现”和“行为验证”绑定在同一次改动中，降低功能退化、性能退化和稳定性退化风险。
- 保持 `Lanymy.Common.AllTests` 持续作为仓库主单元测试入口，而不是让测试职责继续分散。
